# 囚犯实体送餐与自主用餐

本轮补齐食物分配的空间与行动：**狱卒取走真实餐食 → 搬进牢房 → 放在可用位置 → 囚犯自行取餐 → 前往餐位并咀嚼 → 实际消费后补充营养**。倒地或需要医疗卧床的囚犯继续使用床边喂食。优先完成玩法、中断恢复与存读，饥饿阈值、营养、步速及咀嚼时间保持可调。原版依据见 [159 静态机制](159-prison-food-mechanisms.md)。

## 玩家操作

给居民开启狱卒分工后，会为缺粮的饥饿囚犯安排送餐。也可以选中囚犯，在“囚犯供餐”面板选择执行者并下达送餐命令；原护理入口会按病情选择送餐或床边喂食。界面显示谁正在送给谁、食物与份额、取餐或搬送阶段，并可定位计划放餐处。

牢房必须有有效囚犯床和封闭空间，食物来源、囚犯和落点必须符合执行者的允许区域与可达条件。牢房内已有足够食物，或囚犯自己拿着食物时，不再安排重复送餐。自动任务还需要可行动的狱卒、实际可用食物和未被其他照料者占用的目标。

普通送餐不会直接改变囚犯饱食度。囚犯随后在牢房内取用实物，优先寻找可用餐桌旁的餐椅，没有餐位则原地吃饭。食物在咀嚼结束时才被消费；搬送、落地和拿起都不算已经进食。新用餐也接入既有舒适与餐桌记忆。

## 机制连接

| 情况 | 行为 |
|---|---|
| 健康且能自行吃饭 | 狱卒送餐落地，囚犯独立用餐 |
| 倒地或需要医疗卧床 | 到分配床位后使用既有床边喂食，需要实际取餐、到场和喂食时间 |
| 供餐选食 | 使用囚犯的饮食政策；狱卒自己的政策不决定这顿食物 |
| 囚犯自行吃饭 | 沿用原版政策豁免；改变供餐政策不会让已经送来的食物消失 |
| 同房间多个饥饿囚犯 | 汇总缺少的营养与房内可用食物，避免每个人各自重复计算一间满粮牢房 |
| 两名狱卒竞争 | 同一接收者只被一个照料任务占用；来源预约绑定真实堆和实际份额 |
| 狱卒已有可用食物 | 从现有携带批次分出本次份额；多余部分仍留在手中 |
| 途中改政策、允许区域、禁止来源或安排释放 | 取消失效任务、释放预约，已拿到的食物保留 |
| 囚犯死亡、倒地或牢房失效 | 清理不再成立的送餐；之后按新的病情与空间重新安排 |
| 原落点被物品占满 | 在牢房内重新找可达落点；整间无空间时拿着原食物等待 |
| 用餐中取消囚犯床或失去牢房 | 中断用餐，未消费的食物继续保留，不提前结算营养 |
| 存档时正在取餐、送餐、走向餐位或咀嚼 | 保存同一份食物与任务身份，读档重建路径；囚犯用餐路径仍受牢房边界限制 |

供餐与用餐共享已有物品状态，数量、腐败、中毒风险等随真实批次流转。放餐使用原子放置：位置不足不会先扣除携带数量，也不会凭空生成一份“已送达”食物。桌椅占用沿用现有用餐预约，不新增另一套座位账本。

## 原版依据与 Web 适配

原版普通 `FoodDeliver` 的核心是搬运与落地，`FoodFeedPatient` 才在床边完成摄入。本轮修复 v57 文档中明确记录的“健康囚犯也直接喂食”差异。研究对象为本地 RimWorld 1.7.4980 rev60 的程序集与 XML，属于静态派生证据，不等于原版实机验证。

本地原版没有独立 `AllowFood` 字段，本轮也没有新增“允许供餐”开关。释放中的健康囚犯停止普通供餐；倒地者仍可接受床边喂食。原版还有执行等政策与更完整的食物类型，当前 Web 未实现的部分保持明确边界。

原版房内食物估算会计入高于 RawBad 的食物并增加 0.5 营养容差；Web 当前对应简餐、口粮和奶，另按现有可用数量与预约过滤。这一估算不等于每个囚犯已经拿到餐食，也不涵盖完整原版食物等级与特殊食物过滤器。

原版任务中途没有直接持续重查政策、房间总粮和牢房形状。Web 会立即响应政策/区域变更，重查牢房与病情；执行中的送餐不会因为饥饿值稍有变化或另一份食物刚进入房间就反复取消。落点使用确定性、可达、可完整放置的室内格；空间不足时保留并重试，区别于原版的搜索回退与 job cleanup。多层房间识别也沿用 Web 的三维连通与顶棚规则。

## 存档与验证

存档升级至 **v58**。新送餐保存接收者、来源堆、真实份额、落点和取/送阶段；囚犯自主用餐复用已有餐位与咀嚼状态。旧档不创建虚构送餐任务，不改共享饮食或服装政策；原先已在执行的旧喂食任务按原字段继续完成或安全取消。旧版本夹带新任务或新囚犯用餐状态会被拒绝。

验证使用明确记录的受控地形与初始物资，送餐、取食、落地、用餐和中断均经过真实模拟 tick 与公开命令；界面采用 SSR 检查。另从已发布 v57 的真实烹饪与布帽制作中间检查点，分别运行精确历史源码和当前源码，逐 tick 比较完整存档并反复重载，只归一化版本号。

最终测试、静态证据、历史来源和构建身份保存在 [验证回执](evidence/prison-food-voxel-validation.json)。本地复核入口：`node scripts/research/verify-voxel-prison-food-validation.mjs --local`。

新集成文件覆盖 **18 个场景**，包括实际四阶段存读、供餐与自食政策差异、自动分工、双人争用、中断、满地重选落点与等待、商队模板隔离，以及双门牢房存在室外捷径时的用餐路线约束。首轮唯一失败来自双俘虏夹具：先恢复的囚犯漫步占用了第二次捕获的床；改为两人捕获完成后统一恢复，保留全部尝试记录。

首轮全量覆盖 157 文件、2,069 项：2,058 通过、2 失败、9 跳过。旧 Host 测试仍以健康囚犯验证床边喂食，现明确使用需要医疗卧床的清醒囚犯；真正的健康囚犯送餐由上述新集成场景覆盖。另外食物文件的长时收成初始化未完成，墙体取消文件有一项约 5.1 秒处失败；原始 JSON 未提供完整错误文本，不能据此声称是机制断言失败或已证明环境原因。所有尝试保留，以原超时限制单 worker 整文件复跑确认结果。

上述三文件完整复跑 **45/45 通过，无跳过**；收成初始化实际推进 **97,025 tick（8.085 游戏日）**，取得 90 份谷物，每 tick 核对账本，在原 300 秒限制内完成。按所有文件最新完整结果，最终 **157 文件、2,069 项通过**，不拼接不同尝试中的单个成功断言。类型检查与最终构建通过。

真实 v57 历史续跑通过 **750 tick、756 次完整存档比较、5 次重载**，完成一餐与一顶布帽，材料只记账一次。当前执行绑定 109 个源码依赖，历史引擎的 107 个依赖匹配发布凭证。原版独立静态核验覆盖 **30 类型、103 锚点、17 限定检查、12 XML 投影**；其中 17 类型与上一轮食物政策研究哈希一致。这些验证不代表参数已完成平衡。
