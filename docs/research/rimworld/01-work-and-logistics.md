# 工作调度、预留、搬运与寻路

本篇研究本地 RimWorld **1.7.4980 rev60** 的工作与物流链，并对照 Emberfield 当前实现提出设计建议。主要依据为 18 个类型的静态派生代码及 Core XML；未启动游戏、加载存档或验证启用模组后的有效 Def 数据库。程序集 SHA256 为 `eff7d97949f919fb2b151ebfb906e9be749b63410b7dbda78eeebb7972b245c3`。

证据入口：[类型及哈希清单](evidence/work-manifest.json)、[26 项机制结论](evidence/work-claims.json)、[算例输入与结果](evidence/work-cases.json)。下面的 `RW17-WORK-*` 对应文末索引和 JSON。类名后的行号指清单中固定哈希的派生文件，属于**静态推导**，并非原始源码或运行观测。完整派生代码保留在忽略目录 `.local-research/work/`，本篇仅保留机制、公式及必要标识符。

## 1. 总体结构：策略选择与具体执行分开

一个“小人去做饭”的行为，需要依次回答：现在是否应工作、哪些工作启用、哪一种工作先尝试、哪个工位和订单合法、原料与工位能否预留、怎样走到原料和工位、途中失败或被打断后怎样收尾。仅有工作优先级表还不足以覆盖这条链。

```mermaid
flowchart LR
  A[时段与状态] --> B[Think tree 选择]
  B --> C[工作类型与 WorkGiver 顺序]
  C --> D[目标资格与可达性]
  D --> E[创建 Job]
  E --> F[前置预留]
  F --> G[Toils 分步执行]
  G --> H[移动 取货 加工 放置]
  H --> I[完成 失败 暂停 清理]
  I --> B
```

这个流程图是对所审类型的抽象，不代表完整角色 think tree。`ThinkNode_Priority` 按子节点声明顺序取首个有效结果；工作选择内部再遍历提供者。任务开始前做预留，执行期间持续 tick，并在适当时机重选任务、重算路线。[RW17-WORK-04、05、10、26]

对类 RimWorld 游戏的设计意义：让“玩家策略”“任务挑选”“执行状态机”“资源占用”分别有明确的数据结构。这样玩家调整策略时，不必把已经取货、正在赶路或暂停的所有任务都从零重建。该建议是本项目设计推论，不是原作接口规范。

## 2. 工作优先级有多层，数值不能混用

### 2.1 工作类型排序

`Pawn_WorkSettings` 对已启用工作按下面的键降序缓存：

```text
K(workType) = naturalPriority + (4 - manualPriority) × 100000
manualPriority = 0：禁用；1：最高；4：最低
```

因此，在 Core 的数值范围内，玩家手动档位优先于工作类型的自然顺序；档位相同再由 `naturalPriority` 排序。类人角色关闭手动优先级后，启用工作统一按 3 处理，而非每类变成同等随机选择。[RW17-WORK-01、02]

| Core 工作类型 | naturalPriority 声明值 | 对同档位排序的含义 |
|---|---:|---|
| Firefighter | 1400 | 这些类型中靠前 |
| Doctor | 1300 | 在烹饪之前 |
| Cooking | 1000 | 在种植之前 |
| Growing | 700 | 在搬运之前 |
| Hauling | 300 | 在清洁之前 |
| Cleaning | 200 | 这些类型中靠后 |

表内来自 XML 显式声明，不能直接视为任意 DLC/模组组合的最终值。[RW17-WORK-06]

一个工作类型还能有多个 WorkGiver。例如 `GrowerHarvest.priorityInType=100`、`GrowerSow=50`；搬运通用提供者 `HaulGeneral=15`。这些是**类型内部**的声明排序值，不能拿来和手动 1–4 档或 think-tree 分值相比较。[RW17-WORK-07]

### 2.2 emergency 是有条件的分类

缓存构建先找到一个门槛：所有已启用且拥有至少一个非 emergency 提供者的工作类型中，最高的手动优先级，记为 `p*`。只有满足以下条件的提供者进入 emergency 列表：

```text
giver.emergency == true 且 manualPriority(giver.workType) <= p*
```

其余提供者进入普通列表，包括手动优先级较低的 emergency 提供者。Core 中 `FightFires`、`DoctorTendEmergency` 有 emergency 标记，但由此不能断言“任何紧急医疗必定打断所有其他工作”。完整是否打断还取决于外层 think tree、当前任务及角色状态。[RW17-WORK-03、07、26]

### 2.3 时段影响另一层竞争

`JobGiver_Work.GetPriority` 的时段分值为 Anything 5.5、Work 9、Sleep 3、Joy/Meditate 2；无法工作的情形可返回 0。这是与其他行为节点竞争的分值，并不意味着“Sleep 时禁止工作”或“Work 时强制工作到死”。本次未完整展开所有需求节点，不能仅凭这些数字重建整天作息。[RW17-WORK-04]

### 2.4 找目标也有独立规则

提供者先检查资格：角色是否允许该工作、工作标签或类型是否禁用、`ShouldSkip`、必要身体能力，以及机械体等特殊条件。普通 scanner 默认并非 `Prioritized`，也默认不允许不可达目标；默认结束模式为 Touch。[RW17-WORK-05]

cell scanner 的优先模式先看目标的 `GetPriority`，分值相同再比较几何距离平方；非优先模式主要比较该距离，且仍要求目标未禁止、有任务且可达。thing scanner 则走不同的 `GenClosest` 分支，有些情形还优先利用手中已有物。本次未展开 `GenClosest`，因此不把 cell scanner 的规则推广为所有工作的唯一规则。**“最近工作”不等于按实际绕墙路线全局最短。**[RW17-WORK-05]

## 3. 预留是带身份的占用协议

### 3.1 预留什么

`Reservation` 同时记录 `claimant`、`job`、`target`、`layer`、`maxPawns` 和 `stackCount`。目标可以是物体，也可以是格子；数量 `-1` 表示当前全堆。它解决的不只是“这个东西是否被占用”，还包括占用属于谁、属于哪个任务、占用哪一层、允许多少人同时使用、占多少数量。[RW17-WORK-08]

`CanReserve` 先确认角色所在地图、目标有效性、数量是否足够，并处理物理交互预留、已持有足量预留、建筑交互格/座位等特殊情况。之后才统计同目标、同 layer、需要尊重的其他不同 claimant。下面只是这个统计分支的简化条件：

```text
每条相关预留的 maxPawns 必须与本次请求一致
现有相关不同 claimant 数 < 本次 maxPawns
现有相关数量之和 + 本次请求量 <= 当前堆叠量
```

需要尊重哪些角色的预留与派系及 host 关系有关；不能把它理解为所有派系共用一个无条件互斥锁。自己已有足量预留等快捷分支也会影响结果。[RW17-WORK-08]

### 3.2 强制命令与中断

同 claimant、job、layer 的足量重复预留可幂等成功。玩家强制任务若普通预留失败，但忽略其他预留后仍合法，则能登记自身预留并对相关冲突任务发送 `InterruptForced`；有效目标和物品总量等基本约束仍存在。[RW17-WORK-09]

`StartJob` 在创建执行步骤前调用前置预留。执行失败、暂停、正常结束不是同一种清理路径：可暂停任务能够入队并保留预留；其他清理是否释放预留、是否丢下携带物，由参数和任务策略决定。设计时应把“取消”“暂停待恢复”“强制抢占”分别定义，避免资源永久占用或两人同时消费同一份材料。[RW17-WORK-10]

### 3.3 普通搬运比管理器能力更严格

预留管理器支持按数量共享，不代表所有工作都这样使用它。`JobDriver_HaulToCell` 前置预留依次为：**目的格 1 人/-1，然后源物 1 人/-1**。普通搬运会独占源堆与目的格；后续实际拿取量仍受携带能力限制。[RW17-WORK-11、12、13]

## 4. 搬运：仓储策略、拿取量和途中补货

### 4.1 自动搬运的触发与执行

自动搬运先过滤迷雾、操纵能力、不可预留、绑定未完成物、不可达、社会归属不允许取用的食物、火等条件，然后寻找更合适的仓储。格子仓储任务大体分为：预留目的与源物 → 到源物 → 拿取 → 可选追加同类 → 到目的格 → 通过最短任务耗时门槛 → 放置。途中目标消失、禁用变化、储存条件失效都可能让任务失败。[RW17-WORK-11、12]

拿取请求量为：

```text
Q = min(job.count, AvailableStackSpace, source.stackCount)
```

最终以实际成功拿取量更新携带物。`StartCarryThing` 是否从 `job.count` 扣去实取量由参数控制，HaulToCell 显式启用；剩余物是否回队列或解除预留也有参数分支。[RW17-WORK-13]

HaulToCell 的延时条件是到达 `startTick+30` 才进入后续放置阶段。如果途中已经用掉 100 ticks，不再凭这个条件额外等待 30；若只用 10 ticks，就仍未越过该门槛。该常数属于原作 tick，不应直接移植到 Emberfield 的时间尺度。[RW17-WORK-12]

### 4.2 “更好的仓储”首先指更高优先级

普通格子仓储迁移要求目的地优先级严格高于当前仓储。搜索按优先级层次推进，找到高层合格结果后不再为了更短距离降到低层。目的格还要接受该物品，并通过禁用、堆叠/阻挡、预留、火、未完成施工以及可达性检查。[RW17-WORK-14]

这个规则解释了为何“更远的高优先级冷库”仍可以吸走食材，也意味着不能仅因同优先级仓储某格更近就推导出自动重新摆放。

格内选点采用几何距离平方，但存在提前结束：

```text
n = floor(仓储格数 × random(0.005, 0.018))   accurate 模式
n = 0                                     非 accurate 模式
按仓储格列表扫描：
  候选合格且距离不大于当前最好距离时，更新结果
  若此时索引 i >= n，就结束当前组的扫描
```

所以即使参数名为 `needAccurateResult=true`，也不等于穷举所有格子，更不保证按实际路线选到最近格。这里的结论来自循环边界，不是运行表现猜测。[RW17-WORK-15]

### 4.3 两种“顺手搬一下”

| 场景 | 入口与条件 | 设计作用 |
|---|---|---|
| 已在搬同类物，顺便凑满 | `CheckForGetOpportunityDuplicate`；有剩余空间与任务数量；半径 8 内；同 Def 且可堆叠；对象不是满堆；仍须允许、可预留且目的地有效 | 减少零散小堆造成的空跑 |
| 去做另一项工作前先搬一趟 | `TryOpportunisticJob`；任务允许 prefix、非玩家强制、角色有搬运资格，再检查绕路阈值 | 利用本来就要进行的位移 |

第一行属于搬运任务内部追加取货，第二行会插入另一个任务，不能把两者合成一个“8 格顺路搬运”规则。[RW17-WORK-16、17]

第二种规则令角色位置为 P，原工作目标 T，待搬物 I，仓储 S；定义 `D=|PT|`、`a=|PI|`、`b=|IS|`、`c=|ST|`。主要几何约束为：

```text
D >= 3
a <= 30；a <= 0.5D；a + |IT| <= 1.7D
c <= 50；c <= 0.6D
a + b + c <= 1.7D
a + c <= D
```

另外 P→I 与 S→T 各要求在 25 个区域范围内通过检查，物品和仓储也要合法。它从候选列表返回首个合格项，所用距离是几何距离；不能把 `1.7D` 当作整条实际绕墙路径的严格上限。[RW17-WORK-17]

## 5. 施工配送与生产订单

### 5.1 建造材料是需求队列

施工配送会考虑工地缺口、在途投递量与手里已有材料。找到来源后，可合并该来源附近 5 格内的同类资源，并尝试服务 8 格内的邻近工地，形成多来源/目的队列，受携带能力及有效需求约束。目标选择中使用了从资源出发的 Manhattan 距离，但并非完整配送路径的全局最优规划。[RW17-WORK-18]

“地图上有材料”与“这名角色能拿到材料”分开判断。找不到可达资源的失败缓存只覆盖当前 tick，键包含 pawn/resource/forced；不能照搬生产订单较长的重试间隔来解释施工配送。[RW17-WORK-18]

### 5.2 生产订单是工位、配方与人员的联合约束

`WorkGiver_DoBill` 先检查工位能否使用、是否被预留、火与交互格条件；缺燃料时可能转而生成补燃料工作。随后按订单栈顺序检查工作类型、再次搜索时间、允许的角色与技能等条件；部分未完成品还绑定制作角色。原料不齐时，通常将下次搜索推迟随机 **500–600 ticks**，手动菜单检查另有处理。[RW17-WORK-19]

原料搜索半径以工作台为中心，要求距离平方严格小于半径平方，不是“从小人出发找最近若干材料”。区域 BFS 可以在已有候选满足配方时停止；这支持可控的局部搜索成本，但不能据此保证选出的原料总价值、总路程或营养浪费最少。[RW17-WORK-20]

对于本项目，可借鉴的重点是让订单显示具体阻塞原因，例如“缺 6 木材”“入口被封”“指定工人不可用”“燃料不足”，并在相关资源/工位变化时失效缓存。完整复制原作混合营养配料与未完成品恢复流程，不是首轮实现的必要条件。

## 6. 可达性、找路和实际走路是三个问题

### 6.1 可达不等于已算出路线

`Reachability.CanReach` 使用近邻/同 district 快捷判断、区域连接及缓存，特殊模式可走格级检查。它回答能否到达，不直接产出角色逐格行走的路线。工作扫描中频繁使用可达性判断，不等于对每个候选都执行完整路径搜索。[RW17-WORK-21]

### 6.2 本地 1.7 的路径搜索

本版本 `PathFinder` 管理请求与工作任务，`PathFinderJob` 使用优先队列展开允许的格连接；跳过失效队列项和已关闭节点，达到目标区域即生成结果，展开次数受地图格数限制，斜向穿过障碍角也受约束。[RW17-WORK-22、23]

其主要评价式为：

```text
g(next) = g(current) + 格成本(next) + 角色直走/斜走 tick
h = 13 × heuristicStrength × (dx + dz - 0.58579004 × min(dx,dz))
f = g + h
```

常规殖民者 `heuristicStrength=1`；受异常黑暗影响的殖民者分支为 1.5；动物 1.75；其他非殖民者按距离曲线 `(40,1),(120,2)` 求值后取整。角色真实移动 tick 从 pawn 属性传入。虽然类内有 13/18 常量，无 pawn 的实际参数分支却是 **18/18**；不要只看常量名就把所有角色速度写成固定 13/18。[RW17-WORK-22、23]

这些参数、提前终止与关闭节点规则表明，这套实现不能笼统宣传为“任何角色都保证找到全局最短路线”。同样，不应拿旧版文章中另一套寻路实现覆盖本次 1.7 的静态证据。

### 6.3 格子成本如何组合

搜索层的 `IndexCost` 为 `max(grid,providerCost) + (blocked ? 175 : 0)`；providerCost 的 `ushort.MaxValue` 对应 10000。这里名为 blocked 的位图会带来罚分，不能见名就解释为所有相关格子永久不可通行；搜索另有连通性及成本 ≥10000 的拦截。[RW17-WORK-23]

普通地面 `PathGrid.CalculatedCostAt` 从地面成本开始，对物体、雪与适用的沙尘成本取最大值，部分物体有重复路径成本例外；连续经过两扇非自由通行门另外加 45。不可通过的地形、物体或特定围栏返回 10000。[RW17-WORK-24]

`perceivedStatic=true` 时，未附着在其他对象上的火在本格加 1000、邻格每处加 150。这是选路感知罚分。实际入格查询传入 `false`，因此不能把火罚分直接换算为“踩火多站 1000 ticks”。[RW17-WORK-24]

### 6.4 实际移动耗时

设经过基础移动 tick、动态格成本、建筑成本和地形标签倍率处理后的入格成本为 C。先把 C 截到 450，再处理跟随配速或任务 urgency，最后至少为 1：

| urgency | 无同行配速分支时的结果 |
|---|---|
| Amble | `max(3C,60)` |
| Walk | `max(2C,50)` |
| Jog | `C` |
| Sprint | `RoundToInt(0.75C)` |

因此 450 是 urgency 处理前的上限，不是所有最终入格耗时的绝对上限。并且路径估价与实际执行还受不同数据影响，不能把搜索的 `g` 直接当作可靠到达时间。[RW17-WORK-25]

任务跟踪器与路径跟踪器均存在 30 tick 的哈希间隔检查，但不是整套系统统一每 30 tick 才做任何事。前者仍执行当前任务并处理任务到期，后者根据目标移动、路线结束及前方约 20 个节点的阻挡/危险等决定是否重寻路。[RW17-WORK-26]

## 7. 可复算示例

以下均为**合成输入的数学推算**，用于解释机制；不是游戏实测战报。完整输入、预期结果与公式保存于 [work-cases.json](evidence/work-cases.json)。

### 案例 W1：同档位自然顺序与跨档位手动顺序

烹饪 natural=1000、手动 p=2：`1000+(4-2)×100000=201000`；种植 natural=700、p=1：`300700`，所以种植先被尝试。两者都 p=1 时，烹饪 `301000 > 300700`，烹饪先被尝试。若含普通工作的最佳档位是 1，而紧急医疗所属类型 p=2，它进入普通列表；这只说明列表分类，不证明某个时刻最终会选哪一项任务。[RW17-WORK-01、03、06]

### 案例 W2：共享数量与普通搬运的区别

假设同地图、同 layer、相互尊重预留、无物理交互冲突，堆叠 75；已有另一人按 `maxPawns=2` 预留 30。本次请求 45、`maxPawns=2`：已有 1 人<2 且 `30+45=75`，数量分支允许。请求 46 则 `30+46=76>75`，失败。改成 `maxPawns=1` 也因与既有预留配置冲突而失败。普通搬运请求的是 1 人/-1，因此不能用这个共享算例推导两名普通搬运工会同时拆同一堆。[RW17-WORK-08、12]

### 案例 W3：计划搬 80，不等于一次拿到 80

任务剩余 80，可用携带空间 35，源堆只有 20，且实际拿取全部成功，则 `min(80,35,20)=20`。在 HaulToCell 的扣减选项下，剩余任务数量变成 60。这不代表接下来必能补足：还要找到半径内合格的追加目标。[RW17-WORK-13、16]

### 案例 W4：accurate 仓储搜索仍可漏过更近格

一个仓储组有 1000 格，假设本次随机比例为 0.01，则阈值索引 `floor(1000×0.01)=10`。前 12 个索引 0–11 都不合格，索引 12 的格子合格、距物品 20 格，且当前无更好结果；此处即可结束。索引 100 即使距离只有 1 格也不会在这次组内循环被访问。该算例只证明提前退出的可能性，不代表每次仓储选择都会错过最近格。[RW17-WORK-15]

### 案例 W5：直线路上也可能不满足顺路搬运

取 `P=(0,0),T=(20,0),I=(5,0),S=(15,0)`：`D=20,a=5,b=10,c=5,|IT|=15`。全部几何条件成立：`a<=10`、`c<=12`、`a+b+c=20<=34`、`a+c=10<=20`，另外假定资格和区域检查通过，则几何门槛不阻止该任务。若只把 I 改到 `(11,0)`，即使仍在直线上，也因 `a=11>0.5D=10` 被拒绝。[RW17-WORK-17]

### 案例 W6：地面与物体成本不全部相加

假设角色本次直走基础为 13 ticks，地面成本 2，物体成本 27，雪成本 8，无其他修正，则格成本取 `max(2,27,8)=27`，C=`13+27=40`。Jog=40、Walk=80、Amble=120、Sprint=30 ticks。这里的 13 是算例输入，不能称为所有殖民者固定速度。[RW17-WORK-24、25]

### 案例 W7：搜索启发值不是移动时间

当 `dx=10,dz=6,strength=1`，公式得 `h=13×(16-0.58579004×6)=162.30837688`；strength=1.75 时为 `284.03965954`。若另外假设无障碍、直走 13、斜走 18，6 步斜走加 4 步直走仅按这些基础耗时计算为 `6×18+4×13=160`。这说明启发值与给定角色的实际路线成本有不同参数来源，不能混作同一数值。[RW17-WORK-22、23]

## 8. Emberfield 当前差异与建议顺序

下表基于本次读取的项目代码，是**当前实现快照**，不是 RimWorld 行为结论。原型已具备数量预留、多来源取货和取消回滚；建议在现有基础上补足身份与目的地约束。

| 环节 | Emberfield 当前实现 | 与原作审计范围的差异 | 建议 |
|---|---|---|---|
| 工作选择 | `chooseJob` 先处理饥饿、征召、休息、精神疲惫和娱乐，再按手动档位遍历 WORKS | 同档位沿固定 WORKS 顺序；尚无 WorkType/WorkGiver 两层及 emergency 列表 | 先把现有工作拆成有名字的候选提供者，并返回阻塞原因；确认需要后再增加自然顺序 |
| 数量预留 | `reserveItem` 先选足可达多堆再一次增加 `Item.reserved`；`reserveSpecific` 按数量预留 | 数量总额已有；没有通用 claimant/job/layer 记录；`busy` 按任务 kind+target 查角色 | 加入 reservation ID、owner job ID、用途和数量，让取消/恢复可审计 |
| 失败回滚 | `cancel` 释放当前未拿取来源与后续 pickups，并把携带物掉在角色位置 | 已有回滚，但所有取消使用一种丢物逻辑；没有区分保留预留的暂停协议 | 先区分 cancel 与 suspend，再决定哪些任务可恢复 |
| 仓储搬运 | zone=1 是统一仓储；忽略已在其中的物品；单次最多 30；目标按 Manhattan 距离找可达格 | 无仓储过滤器、等级及目标格/容量预留；普通任务这里采用部分数量预留 | 优先补目标容量与预留，再增加仓储等级/过滤器 |
| 多来源执行 | `act` 支持逐个 pickup、拿取、重寻路和运往工位/仓储 | 原型已有批量取货基础；缺少通用的顺路插入与邻近多工地配送策略 | 先改进已有来源选择；把“凑同类”和“插入搬运”作为两个可选功能 |
| 寻路 | 四邻接、Manhattan 启发、固定边成本 1、二元 blocked、复用数组与堆 | 尚无斜向、地形权重、门/危险/角色移动差异 | 地形开始影响玩法时再引入权重，保持小地图的可解释性 |
| 失败重试 | 任务未选出后等待 40 个本项目 ticks；极端饥饿可中断 | 缺少按资源/工位失效的专门缓存 | 将“没有资源”“目标被占用”“路径封闭”拆开，按不同事件重试 |

代码位置：[world.ts](../../../src/sim/world.ts) 的 `busy/reserveItem/cancel/take/chooseJob/workJob/act`（本次分别约 463、483、505、522、573、803、919 行），[defs.ts](../../../src/sim/defs.ts) 的 WORKS 定义，以及 [path.ts](../../../src/sim/path.ts) 的四邻接寻路。后续代码修改后应以函数名重新定位。

建议按可见收益推进：

1. **正确性**：明确任务身份、预留归属和目的容量；覆盖取货前取消、取货后取消、来源消失、目的地失效四类转移。
2. **可解释性**：每次候选失败携带结构化原因，UI 显示具体缺口；避免把所有问题归成“暂无工作”。
3. **策略空间**：仓储优先级与过滤器、生产订单的员工/半径限制，使布局和分工成为玩家选择。
4. **效率与表现**：在基础链路稳定后增加同类凑货、附近工地配送和有约束的顺路搬运。
5. **规模化**：只有地图/角色规模或地形玩法要求时，再扩展分区可达性、加权路径、批处理与更复杂缓存。

以上为 Emberfield 方案建议，尚未在此研究任务中实现或测试。原作的 30、500–600 ticks 和 13/18 等数值应保留为研究基准；本项目应按自己的仿真频率和目标节奏重新标定。
