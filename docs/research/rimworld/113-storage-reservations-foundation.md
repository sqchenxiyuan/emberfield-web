# 多堆仓储之前：物资预约与放置基础

2026-11-04。本文记录 Emberfield 的机制实现；原版事实分别见[111 静态机制](111-shelf-storage-mechanisms.md)和[112 实机记录](112-native-shelves-runtime.md)。**本次仍使用 v36 存档；实体货架、架面三槽及邻接取放还未开放。**

用户要求初期以玩法和机制为主。这里先解决仓储、建造与进食之间的物资竞争，保留成本、工速、堆上限和时间比例，后续再调整经济节奏。

## 具体物资与数量的预约

建造、生产取料和找食物现在出发前记录 `Stack ID + 数量`，搬运同时记录源堆数量和目的仓位。照护、驯养喂食、原地进食也参与同一源堆的可用量计算；人物不能把别人已预约的数量当成空闲库存。

例如一个木材堆有 12 单位、每面墙需要 6：两个工人可各预约 6，第三人等待。只有 6 单位时，不会同时派多个人去拿同一份。征召或任务中断会释放该人的预约，其他人可以接手。餐食也是按份分配；一个人预约最后一份饭后，其他人寻找另一堆可用食物。

到达时必须仍能找到原 ID。交易、燃烧、环境劣化或腐坏移除源物时，会取消相关取货计划；同格后来出现的新堆不会继承旧计划。数量减少时，普通取料和搬运重新安排；已有原地进食若预留份量仍然足够则继续。装备、药物和喂食的既有身份检查继续使用。

普通取料/搬运预约仍是临时路线状态。读档后重新规划，物品、携带批次及已配送材料维持原有持久化规则；本次没有重排旧物品 ID，也没有新增存档库存副本。

## 单堆上限与一格多个槽分别计算

新增统一的格内放置算法：先填充所有兼容的未满堆，再用空槽生成符合单堆上限的新堆。同格不同资源、不同作物、装备实例保持独立；不把木材 75 的单堆上限改成 225。

预约也通过同一算法逐笔预演。例如三槽格中有稻米 70，随后预约稻米 70、玉米 75，则稻米占两槽，玉米占第三槽；钢材不能再预约，但已有稻米仍能补 10。两名工人的同种资源可以共享未满堆，不能简单按预约人数扣槽。

真实放置先在副本里安排整批货物；只有所有批次都能放下才提交。失败不改库存、品质/耐久、食物年龄、污染率或全局 ID。合并按实际转移量计算状态，实例物品不合并。放置与仓位查询使用每次操作的临时格索引，避免逐个候选格反复扫描全部物品，也避免长期缓存错过物品变化。

算法已有三槽案例验证，但游戏世界目前调用的容量仍是 **1**。不能把这些规则测试当作货架已经可建造的证据。

## 本地验证与边界

新增测试覆盖稀缺建材、按数量共享及征召释放、多人分餐、交易后同格替代物、腐坏中断，以及三槽混合物资、补堆、加权食物状态、实例身份和超容量存量。旧物流场景继续覆盖满仓等待、改筛选、施工置换失败回滚、携货进食、跨层搬运和真实旧档迁移。

本地验证通过：全量 **100 个文件、1,253 项测试**；其中新增 13 项机制回归。生产构建及文档链接校验通过。正常指令经营包含 **19 条命令、12 项检查、2,028 tick**，另将未改动的原 v5 冷库档迁移并推进 240 tick，数量与加权年龄保持。真实 Chrome 的 Worker/main 各 **9 项检查**通过，错误均为 0，分别核对 6/5 个资源与本地构建字节相同；查看了满仓与地下仓储截图。

规则测试使用显式几何/物资夹具；经营验证从历史开局档执行普通指令，浏览器通过鼠标、键盘和文件选择器操作，`window.voxel` 只读用于检查。没有把夹具或纯算法测试说成原版运行证据。

命令如下（`test-results` 是本地输出，不作为原版证据）：

```powershell
npm test
npm run build
$env:VOXEL_LOGISTICS_OUT = 'test-results/shelves-foundation-campaign'
node scripts/voxel-logistics-campaign-verify.mjs
$env:VOXEL_LOGISTICS_BROWSER_OUT = 'test-results/shelves-foundation-browser'
$env:VOXEL_TEST_URL = 'http://127.0.0.1:4196/?world=voxel'
node scripts/voxel-logistics-browser-verify.mjs
```

旧物流验收脚本的版本断言曾停留在 v21，更新为核对当次模拟导出的版本；同时允许并验证后来加入的物资耐久/污染字段，损失账本包含实际损毁。原 v5 文件哈希、数量、加权年龄和跨层物理搬运断言保留。

全量回归中，双份五日生态模拟触发原来的 30 秒限制。使用已发布 `ee891ea` 的源码覆盖进行同场景对照也耗时约 31.2 秒；修改前的本次代码约 31.8 秒。仅将该用例的时间预算改为 60 秒，仍推进 120,000 个完整模拟 tick 并检查重载确定性；没有减少场景或改动生态参数。这是本机运行余量，不是性能提升结论。

测试只在本地运行，Pages 流水线继续安装、类型检查/构建和部署。

## 后续货架的验收范围

下一阶段需要加入独立无品质货架实体、整架共享筛选和两种占地，把人物站位与物品格分开，逐一连接吃饭、生产、照护、驯养、装备和交易。随后连接满架卸装、烧毁后的可保存散货、环境保护、旧档迁移及多堆可见/可选的界面。完成普通建造→入库→实际取用→改筛选→满架搬迁→读档链条后，才能宣布货架玩法完成。
