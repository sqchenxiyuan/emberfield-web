# 房间、温度与电网：从空间布局到生存约束

本篇对应本地 RimWorld `1.7.4980 rev60`，分析对象是 `Assembly-CSharp.dll` 的静态派生代码与 Core XML；未启动游戏、加载存档或解析启用模组后的完整 Def 数据库。程序集、工具和 20 个派生类型的哈希见 [environment-manifest.json](evidence/environment-manifest.json)，逐项可核查的结论见 [environment-claims.json](evidence/environment-claims.json)。派生行号仅适用于该清单中的哈希；完整派生代码留在忽略目录 `.local-research/environment/`，可用仓库提取脚本在自有安装上重建。

下文 `类名:行号` 指该类型派生文件的行号，属于**静态推导**，不是原始源码或运行记录。`[E01]` 等编号对应结论清单中的 `ENV-E01`。XML 值均为**声明值**；代码默认值、XML 显式覆盖和后续补丁要分别处理。算例属于给定输入下的数学推导，忽略条件均在案例旁列出。

## 1. 房间是共享数据单元，三种“室外”判定不同

`Verse.Room` 保存/引用区域、温度跟踪器和房间属性缓存。物体增删、地面变化等事件标记属性缓存失效；`GetStat` 才按需要更新。更新时，基本属性先于依赖属性计算，房间用途取各 `RoomRoleWorker` 得分最高者；不满足 `ProperRoom` 或超过 60 个 Region 时改用各属性的 `roomlessScore`。因此不是每次 UI 绘制都扫描全部房间。[E01]

| 判定 | 静态条件 | 影响 |
|---|---|---|
| `UsesOutdoorTemperature` | 接触地图边界；或 `OpenRoofCount >= ceil(CellCount × 0.25)` | 热交换直接采用室外温度；普通推热/温控不改变这个房间 |
| `OutdoorsForWork` | 未盖顶格数 >100；或未盖顶格数 >房间格数×0.25 | 作业系统的室外判定，不能替代温度判定 |
| `PsychologicallyOutdoors` | 未盖顶格数 ≥300；或接触地图边界且未盖顶比例 ≥0.5 | 心理空间相关判定，空间属性直接取350 |

证据：`Verse.Room:99–108, 378–402`。[E02] 例如100格房间缺25格屋顶就达到室外温度阈值；25格房间缺6格尚未达到，缺7格达到。**“盖了部分屋顶”不等于热学室内，“热学室外”也不等于工作或心理室外。**

## 2. 豪华度：均衡建设、短板与空间约束

### 2.1 四个基础量

| 输入 | 已确认计算方式 | 容易误解的边界 |
|---|---|---|
| 财富 `W` | 房内及相邻对象中，建筑/植物的市场价×堆叠数，加各格地面市场价 | 此处不遍历加入普通 Item；它不是整张地图用于袭击的财富 |
| 美观 `B` | 房内各格、部分相邻对象格的美观总和，使用集合避免重复计算对象；除以格数曲线 | 分母不是总等于面积；40格以内为 `20 + N/2`，40格及以上为N |
| 空间 `S` | 可站立格每格+1.4；否则若普通可走格每格+0.5；上限350 | 家具占位通过可站立/可走状态间接影响；心理室外直接350 |
| 清洁 `C` | 建筑/物品/污物/植物的清洁度×堆叠数，加地面清洁度，除以房间格数 | 清洁度可负；不是只统计垃圾数量 |

证据：五个 `RoomStatWorker_*` 类，见 [E03–E06]。美观分母的分段值由曲线节点 `(0,20),(40,40),(100000,100000)` 推得，格子内部具体美观项目仍由未展开的 `BeautyUtility.CellBeauty` 决定。

### 2.2 豪华度公式

定义带符号对数压缩函数：

```text
f(x) = x                       当 |x| < 1
     = 1 + ln(x)               当 x >= 1
     = -1 - ln(-x)             当 x <= -1

a = f(W / 1500)
b = f(B / 3)
c = f(S / 125)
d = f(1 + min(C, 0) / 2.5)

q = 0.65 × mean(a,b,c,d) + 0.35 × min(a,b,c,d)
若 q > 5c：q = 0.25q + 0.75 × 5c
豪华度 I = 100q
```

证据：`RoomStatWorker_Impressiveness.GetScore/GetFactor:8–35`。[E07] 这里有三个设计结果：改善最差项很有效；财富与美观超过基准后收益对数递减；狭小空间限制靠堆贵重物品补分。清洁度超过0不再增加豪华度，但仍可能改善医疗和研究。

Core 的豪华度阶段下界依次声明为：20、30、40、50、65、85、120、170、240，低于20落在首阶段；原文标签从 `awful` 至 `wondrously impressive`。阶段是 UI/其他系统的输入，不能把“豪华度+10”等同于“心情+10”；不同房间用途如何转化心情，本篇未追踪。[E08]

### 2.3 清洁度是一项跨系统投资

`Rooms/RoomStats.xml` 声明以下依赖清洁度的曲线节点：[E09]

| 属性 | 节点 `(清洁度,输出)` | 解释边界 |
|---|---|---|
| `InfectionChanceFactor` | (-5,1), (0,0.5), (1,0.2) | 感染概率因子，不是最终感染概率 |
| `SurgerySuccessChanceCleanlinessFactor` | (-5,0.6), (0,1), (1,1.10), (5,1.15) | 手术洁净因子，不是最终成功率 |
| `ResearchSpeedFactor` | (-5,0.75), (-2.5,0.85), (0,1), (1,1.15) | 研究速度乘子输入 |
| `FoodPoisonChance` | (-5,0.05), (-3.5,0.025), (-2,0) | 房间贡献声明；不代表厨师/材料导致的食物中毒概率为零 |

这些是 XML 声明曲线。本篇未展开 `RoomStatWorker_FromStatByCurve` 及每项消费位置，不能据此宣布完整医疗/研究公式已经还原。

## 3. 温度：房间级状态与分层交换

### 3.1 状态与热容量

每个房间通过 `RoomTempTracker` 持有一个温度；设值裁剪到 `[-273.15,1000] °C`。`Room.PushHeat(E)` 对热学室内执行 `ΔT=E/CellCount`，对采用室外温度的房间返回false。这里的E是游戏热量单位，不应当作真实焦耳。[E10]

`ControlTemperatureTempChange` 也按格数分摊，但将温差限制在目标温度：加热不会越过目标，也不会反向制冷；制冷同理。面积越大，同一设备单次改变温度越小。[E11]

`RimWorld.Planet.RoomTemperatureVacuum` 只是保存 `roomCell/temperature/vacuum` 的可序列化结构，不是热交换算法主体；本版本的主体仍是 `Verse.RoomTempTracker`。[E12]

### 3.2 四类自然交换

常量声明房间温度交换间隔为120 tick。`EqualizeTemperature` 在普通室内计算以下四项后相加；门道有单独分支。调度器的实际调用路径本篇未提取，因此这里是**每次方法调用、按120 tick标定**的更新量。[E13]

记 `D=室外温度−当前温度`，有：

```text
D' = D                                  当 |D| < 100
   = sign(D)×100 + 5×(D-sign(D)×100)     其他情况

薄顶项 = D' × 薄顶比例 × 0.00005 × 120
无顶项 = D' × 无顶比例 × 0.0007 × 120
厚顶项 = min(15−T,0) × 厚顶比例 × k × 120
  k = 0.002，若地图生成器 isUnderground
      0.00005，其他情况
```

证据：`RoomTempTracker:254–296`。[E14] 厚顶项只将**高于15°C**的房间向15°C冷却；低于15°C时该项为0，不会自动把冷冻库加热到15°C。无顶比例达到室外判定阈值后不再继续套用这个室内公式。

墙体交换另用边界抽样：先从房间格沿四方向寻找距离2格的候选，排除部分Portal和仍与本房间相连的格；打乱候选并每次轮转检查 `ceil(候选数×0.2)`。普通环境下采样目标有空气温度则用 `目标T−室内T`；取不到直接空气温度则用 `0.5×(室外T−室内T)`。最后乘：

```text
墙体 ΔT = 平均采样温差 × 候选总数 × 120 × 0.00017 / 房间格数
```

证据：`RoomTempTracker:116–174, 215–251`。[E15] 不能从这段代码直接推出“某种墙材导热系数”：本段没有按钢/石/木读取不同材料导热率。双层墙会改变候选格获取路径，但复杂墙角/门道布局的实际结果还需要布局测试。

真空地图的墙体分支将温差额外乘 `0.00005`；通过建筑交换时，向低温方向的变化另有0.1系数。真空暴露、漏气和重力船系统还有其他链路，本篇只确认这些温度分支，不称为完整太空环境还原。[E15,E16]

### 3.3 门和通风的公共交换函数

`GenTemperature.EqualizeTemperaturesThroughBuilding` 收集两侧或四邻接的不同房间，以**不按面积加权的平均温度**为驱动目标；各房间的变化量再除以自身格数，并通过共同缩放因子防止小房间一次越过平均值。建筑自身占用房间的温度设为该平均值。[E16]

`TemperatureTuning` 声明开门间隔34 tick、关门375 tick、门交换率1、通风口交换率14，但本篇未提取 `Building_Door/Building_Vent` 的调用条件。这些只能登记为调参常量，不能假定所有门始终按该速率交换。[E17]

## 4. 恒温设备：热流、效率与耗电是不同量

Core 显式声明：[E18]

| 建筑 | 电力声明 | 热量参数 | 建造材料 |
|---|---:|---:|---|
| Heater | 175 W | +21 单位/秒 | 钢50、工业零部件1 |
| Cooler | 200 W | −21 单位/秒 | 钢90、工业零部件3 |

`CompProperties_TempControl` 默认目标21°C，可调范围默认−50至50°C，低功耗系数0.1；以上两个设备XML没有覆盖这些字段。标准 Rare 调用中的乘数为4.1666665，因此每次方法调用基础热量绝对值约87.5。若温控返回非零温差，设备按额定功耗工作，否则改为额定×0.1：对应17.5W/20W。[E19,E20] 这不是“达到目标就完全断电”。

**加热器效率：** 当前温度≤20°C时1；20至120°C线性降至0；高于120°C为0。单次热量为 `21×效率×4.1666665`，再交给目标裁剪。[E20]

**冷气机效率：** 令排热侧温度H、制冷侧温度C：

```text
差值 d = max(H−C, H−40) = H−min(C,40)
效率 η = max(0, 1−d/130)
可用冷量 E = −21 × η × 4.1666665
制冷侧实际 ΔT = 按目标温度裁剪(E / 冷侧房间格数)
若实际 ΔT != 0：排热侧 PushHeat(−E × 1.25)
```

两个出风格任一不可通行时不进行温控，并进入低功耗。效率没有显式上限1，排热侧比冷侧更冷时可以超过1。排热取的是**本轮可用冷量E**，并非目标裁剪之后的实际取热量；接近目标时尤其不能用理想物理热泵守恒式替代这段游戏规则。[E21]

食物腐烂的温度公共函数为：温度≤0°C时0；0至10°C线性 `T/10`；≥10°C时1。只确认这个倍率函数，不等同于全部食物的完整保质期公式。[E22]

## 5. 电网：以W和Wd结算，短缺时分批关闭设备

### 5.1 单位和电池

`CompPower.WattsToWattDaysPerTick = 1.6666667E-05`，近似 `1/60000`；设备每tick能量为 `PowerOutput × 系数`。发电为正、用电为负，电池以 **Wd（瓦·游戏日）**储能。不要把600 Wd误读成600 Wh。[E23]

Core Battery 显式覆盖容量600 Wd、充电效率0.5；C#类默认容量1000只适用于没有被XML等覆盖的情形。其他声明包括钢70、零部件2、雨中短路、传导电力、EMP击晕组件。[E24]

`CompPowerBattery` 的规则：[E25]

- 每tick自放电 `min(5×WdPerTick,当前储能)`，即持续5W的能量损失。
- 接受输入容量为 `(上限−储能)/效率`；实际加入储能为输入×效率。放电不再乘一次50%。
- 故障或EMP时可接受充电量为0；发生 `Breakdown` 信号时已有储能被清空。
- `CurrentStoredEnergy` 不把EMP电池计入可用总能量。放电内部列表却只筛储能>ε，没有在该函数再次排除EMP；不能将局部代码概括成“EMP电池在全部链路彻底隔离”，这个边界应运行验证。

### 5.2 电力平衡与启停

每个网络先求 `g=已开启设备的每tick净产能`、`s=当前可用储能`。[E26]

1. 若 `s+g >= −1e−7` 且未被游戏条件禁电，正常结算；富余能量分配给电池，赤字从电池提取。
2. 若有待启动设备，且缓冲测试通过，按 `max(30, floor(200/待启动数量))` tick间隔尝试启动。每次随机尝试 `max(1, round(数量×0.05))` 个；逐个检查是否承担得起其本tick消耗。
3. 缓冲测试有一个细节：有电池且可用储能≥0.1时先减5 Wd，再检查余量。这是启动迟滞的局部条件，不能简化成任何状态都“电池≥5才通电”。
4. 能量不足或禁电分支每20 tick收集当前开启的负功率设备，随机尝试关闭约5%，至少1个。不是整个网络同时全部熄灭，也没有在这里按“医院优先”分级。

随机选择可抽到重复设备，因此“尝试5%”不保证每次恰好关闭5%的不同设备。充电分配会打乱电池列表，按剩余可接受输入容量逐批均摊；一部分满后再给其余电池，非固定把第一个充满再轮下一个。[E27]

电网连接的拓扑重建、太阳能/风力曲线、短路爆炸概率与故障频率未在本篇展开；不能从电池XML的 `shortCircuitInRain` 声称已经还原“滋滋”事件完整机制。

## 6. 可复算的案例

案例数值详见 [environment-cases.json](evidence/environment-cases.json)。这里全部是静态公式算例，没有运行时截图或实测帧率含义。

1. **均衡房间与脏污短板。** W=1500、B=3、S=125、C=0时，四项均为1，豪华度100。只把C降到−2.5，清洁因子归零，豪华度变48.75；C从0提高到1仍是100。财富、美观相同，清洁收益取决于目标是豪华度还是医疗/研究。
2. **狭小昂贵房间。** W=1500、B=3、S=7、C=0，四项为1、1、0.056、1。混合得q=0.5162，超过空间阈值0.28，再惩罚至0.33905，豪华度33.905。这里S是空间分数，不能直接当7格面积。
3. **屋顶的边际价值与阈值。** 非真空室内20°C、室外0°C，忽略墙和厚顶项：全薄顶每次交换−0.12°C；90%薄顶/10%无顶为−0.276°C。100格缺25格屋顶时已转室外判定，不能继续以线性损失估算。
4. **加热和排热。** 25格房间0°C、目标21°C、无热损失，一次加热约+3.5°C。冷气机冷侧10°C、热侧40°C、冷侧25格、目标足够低，效率10/13，单次约−2.6923°C，向热侧推热84.1346单位。若目标仅9.9°C，冷侧实际只降0.1°C，但上述代码仍推同一轮84.1346单位热量。
5. **电池续航与回充。** 单个600 Wd满电池、恒定400W负载、无发电，计5W自放电，理想连续续航 `600/405=1.48148`游戏日，约35.56游戏小时。持续1000W富余电力给空电池回充，净储能速度 `1000×0.5−5=495 Wd/日`，约1.21212日充满。这里忽略启停缓冲、逐tick先后顺序、EMP及故障；不是现实墙钟时长。

## 7. 对 Emberfield 的设计意义和实现差距

当前实现核对位置：[`src/sim/world.ts`](../../../src/sim/world.ts) 的 `temperature/environment/power`，以及 [`src/sim/defs.ts`](../../../src/sim/defs.ts) 的 cooler/battery 定义。下面是本次阅读时的状态，不是待办已完成承诺。

| 子系统 | 当前Web原型 | 下一阶段可采用的结构 |
|---|---|---|
| 房间 | 未见房间聚合评分和用途系统 | 网格连通分区→Room ID→属性脏标记；基础属性先算，再算豪华度/用途 |
| 温度 | 全局天气温度；冷藏柜4格内腐败倍率0.25 | 每房间一个温度与屋顶比例，低频更新边界交换；UI显示目标/当前温度 |
| 热设备 | 距离光环式冷藏，额定150W | 热流输入、目标裁剪、低功耗待机、双侧排热与阻塞分离 |
| 电池 | 每个4kWh，充电效率80%，未见自放电 | 显式统一单位；可保留自有平衡，但不能标成原版600 Wd/50% |
| 电力短缺 | 网络整体 `powered` 布尔；逐电池顺序充放电 | 保留每设备开关状态、启停缓冲和可测试的分批负载策略 |

设计推论：房间级状态、变化时失效的缓存、轮转边界抽样适合浏览器内存约束，不需要把温度做成每格复杂流体场。不同系统使用不同“室外”谓词则适合保留显式函数，避免单个 `indoors` 字段把行为错误耦合。它们是参考原版组织方式的实现建议，不是已验证的Web性能结论。

建议第一条可验证实现链为：墙/门/屋顶变化→房间重建→保存能量语义→恒温设备→腐烂倍率→停电导致升温。先让玩家能用布局改变结果，再逐步加入豪华度、清洁度与医疗。无需为了“复刻数值”立刻加入真空和重力船分支。

## 8. 仍需补证

- `RoomTempTracker` 的实际地图调度、房间分裂/合并时温度迁移和顺序敏感性；文中120 tick是常量和方法标定。
